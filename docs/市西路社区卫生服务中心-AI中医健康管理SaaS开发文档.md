# 市西路社区卫生服务中心 AI 中医驱动数字化获客与健康管理 SaaS 开发文档

## 1. 文档概述

### 1.1 文档目的
本文档用于指导“市西路社区卫生服务中心 AI 中医驱动的数字化获客与健康管理闭环”SaaS 系统的产品设计、技术研发、实施交付与后续迭代。文档目标是把院方业务方案沉淀为一套可开发、可验收、可复制、可规模化的系统蓝图，支撑项目从样板点建设走向标准化复制。

### 1.2 项目定位
项目定位为“AI 中医驱动的社区健康管理样板点”，以“系统 + 运营 + 组织 + 商业”闭环能力为核心交付物，帮助基层医疗机构从“以医疗为中心”转向“以健康管理为中心”，实现：

- 对存量居民健康档案与慢病人群的持续触达。
- 对新增客户的低成本获客、沉淀与转化。
- 对服务流程、交付质量与经营结果的标准化与可复制化。

### 1.3 建设目标

#### 业务目标
- 建立以四诊仪、体质辨识、慢病风险筛查为入口的获客体系。
- 建立以居民个人与家庭为单位的长期健康管理体系。
- 建立 AI 随访、异常预警、复诊转诊、服务续费的闭环转化体系。
- 建立面向院方管理层的数据看板、SOP、台账与可审计体系。

#### 系统目标
- 打造支持多活动、多角色、多服务包、多站点协同的 SaaS 平台。
- 构建覆盖“活动获客—建档分层—健康管理—随访预警—复诊转诊—增购续费”的业务链路。
- 实现标准化能力配置，支撑未来向其他社区卫生服务中心复制。

### 1.4 适用对象
本文档面向以下角色：
- 产品经理
- 架构师
- 前后端开发工程师
- AI/算法工程师
- 测试工程师
- 项目实施与运营团队
- 院方项目负责人、信息科、公卫负责人

## 2. 业务背景与核心问题

### 2.1 行业背景
基层医疗正从被动诊疗转向主动健康管理，重点不再是低频院内服务，而是围绕居民日常生活开展连续、可经营的健康服务。该项目需要把一次性医疗行为转化为可持续的健康服务关系，通过数字化系统把服务延伸到院外、家庭与日常场景。

### 2.2 需要解决的三类问题

#### 2.2.1 存量沉默
- 已有健康档案未被激活。
- 慢病重点人群触达依赖人工，效率低。
- 随访质量不稳定，执行差异较大。

#### 2.2.2 增量乏力
- 获客方式单一，活动结束即流失。
- 线下活动难沉淀为长期私域关系。
- 复购、续费、转介绍弱。

#### 2.2.3 服务不可复制
- 医生与站点服务方式不统一。
- 活动流程、随访策略、标签规则缺少标准化。
- 管理层难以量化评估成效与复制能力。

### 2.3 产品价值主张
通过 AI 中医、数字化获客、连续监测与标准化运营能力，形成一套可运营、可追踪、可量化、可复制的基层健康管理 SaaS 系统。

## 3. 产品总体方案

### 3.1 总体打法
平台总体打法分为三层：

1. **前端获客层**：以四诊仪、体质辨识、活动筛查、内容矩阵、数字人 IP 建立信任入口与线索池。
2. **中台运营层**：以居民档案、家庭档案、风险分层、服务包、AI 随访、群运营 SOP 完成交付。
3. **经营分析层**：以数据看板、履约台账、经营台账、SOP 迭代支撑验收与复制。

### 3.2 产品形态
建议系统采用“多租户 SaaS + 医疗业务配置化 + AI 服务中台”架构，面向以下终端提供能力：

- 管理后台：院领导、项目管理员、运营人员使用。
- 医护工作台：家庭医生、健康管理师、公卫人员使用。
- 居民端：微信服务号/公众号/小程序承接。
- AI 服务层：AI 客服、AI 医师助手、数字人内容生成引擎。
- 设备接入层：四诊仪、手环、检测设备、人工录入接口。

### 3.3 核心闭环
核心闭环可抽象为：

**活动触达 → 到场核销 → 指标采集 → 报告生成 → 风险分层 → 建档入群 → AI 激活 → 健康管理 → 异常预警 → 人工介入 → 复诊/转诊 → 服务续费/增购 → 数据复盘**

## 5. 业务模块设计

## 5.1 获客与活动管理模块

### 5.1.1 活动模板中心
用于沉淀标准活动模板，支持一键复用。预置活动模板建议包括：
- 市西中医康复季
- 青少年鼻炎关爱季
- 市西公益检测日
- 慢病筛查日
- 体重管理经营活动
- 睡眠与情绪讲座
- 中医体质辨识周
- 企业/养老机构筛查专场

功能点：
- 活动模板创建、复制、启停。
- 活动海报、报名表单、宣发文案模板管理。
- 活动流程配置：报名、签到、检测、报告、入群、回访。
- 活动统计：报名人数、到场率、建档率、入群率、转化率。

### 5.1.2 活动执行管理
- 活动报名与预约时间管理。
- 现场签到核销。
- 检测项目登记。
- 报告自动生成与推送。
- 参与者标签自动打标。
- 活动结束后的 7 天激活任务自动生成。

### 5.1.3 线索管理
- 渠道来源管理：公众号、视频号、线下活动、转介绍、企业合作、养老机构等。
- 线索状态流转：新线索、已触达、已到院、已建档、已入群、已签约、已流失。
- 跟进记录、负责人分配、提醒机制。

## 5.2 中医四诊与评估报告模块

### 5.2.1 设备与人工数据接入
- 四诊仪数据接入。
- 体质辨识问卷。
- 基础指标录入：血压、血糖、血氧、心率、体重、腰围等。
- 检验检查结果录入或导入。

### 5.2.2 报告引擎
- 生成中医体质辨识报告。
- 生成慢病风险初筛报告。
- 生成生活方式风险提示。
- 支持居民端查看、下载、分享。
- 支持医生端补充结论与建议。

### 5.2.3 标签体系
标签分三类：
- 基础标签：年龄、性别、家庭结构、疾病史。
- 行为标签：是否入群、是否完成打卡、是否复诊、是否有购买记录。
- 风险标签：高血压风险、糖代谢风险、睡眠风险、肥胖风险、情绪风险、中医体质类型。

## 5.4 风险分层与服务分级模块

### 5.4.1 风险分层
建议按照高、中、低风险三层进行配置，并允许各租户自定义规则。

可配置输入项：
- 四诊结果
- 体质辨识结果
- 基础生命体征
- 慢病史
- 年龄与家庭史
- 连续监测数据
- 近期异常事件

### 5.4.2 服务分级
建议将服务定义为一、二、三级，分别对应不同随访强度与人工介入程度。

| 风险层级 | 服务等级 | 随访频率 | 触达方式 | 人工介入 | 推荐服务 |
|---|---|---:|---|---|---|
| 低风险 | 一级 | 每月 | AI 为主 | 低 | 基础管理包 |
| 中风险 | 二级 | 每周 | AI + 管理师 | 中 | 强化管理包 |
| 高风险 | 三级 | 每日/按需 | AI + 管理师 + 医生 | 高 | 强化管理包 / 复诊转诊 |

### 5.4.3 分层规则引擎
- 规则可配置。
- 支持阈值、组合条件、评分模型。
- 支持自动分层与人工调整。
- 支持分层变更通知与任务重编排。

## 5.5 健康管理与随访模块

### 5.5.1 随访计划管理
- 按风险等级自动生成随访计划。
- 支持模板：7 天激活、14 天巩固、月度复盘、专项干预。
- 支持图文、表单、问卷、消息、电话、视频等触达方式。
- 支持任务派发给 AI、健康管理师或家庭医生。

### 5.5.2 AI 随访引擎
- 自动发送健康提醒。
- 自动收集反馈与打卡数据。
- 自动识别居民意图：咨询、预约、异常、续费、投诉。
- 自动生成随访摘要。
- 对超出规则范围的问题转人工。

### 5.5.3 异常预警管理
- 设置指标阈值和组合预警规则。
- 预警分级：提醒、关注、紧急。
- 自动通知责任人。
- 自动生成处置工单。
- 闭环记录：预警时间、响应时间、处置结果、复盘结论。

### 5.5.4 医护协同工作台
- 家庭医生查看重点居民清单。
- 健康管理师执行日常随访任务。
- AI 助手给出任务建议与摘要。
- 转诊、复诊、加项服务推荐留痕。

## 5.7 数字人与 AI 内容中台模块

### 5.7.1 数字人能力范围
- 专家 IP 宣教视频生成。
- 活动宣发视频生成。
- 标准化随访说明视频。
- 居民常见问题答复。

### 5.7.2 内容生产流程
选题池 → 脚本生成 → 医疗审校 → 数字人生成 → 发布排期 → 效果追踪

### 5.7.3 合规要求

## 6. 关键业务流程设计

### 6.1 活动获客流程
1. 配置活动模板。
2. 生成活动报名页与宣发物料。
3. 居民报名并预约。
4. 到场签到核销。
5. 四诊或基础指标采集。
6. 自动生成报告并推送。
7. 自动打标与风险初筛。
8. 引导入群与建立个人/家庭档案。
9. 自动生成 7 天激活任务。
10. 进入长期健康管理流程。

### 6.2 健康管理流程
1. 采集连续数据与问卷反馈。
2. 系统自动进行风险分层。
3. 绑定服务等级与随访计划。
4. AI 发起随访与提醒。
5. 异常预警触发责任人处理。
6. 医生/管理师人工介入。
7. 复诊/转诊建议与预约。
8. 月度复盘与服务续费。

### 6.3 家庭群运营流程
1. 建立家庭档案。
2. 绑定家庭成员关系。
3. 生成家庭画像。
4. 拉入家庭健康群。
5. 推送家庭任务与共性建议。
6. 推动家庭方案包签约或续费。

### 6.4 异常预警闭环流程
数据异常 → 规则命中 → AI 初步判别 → 责任人接收预警 → 人工回访 → 处置记录 → 复盘归档

## 7. 系统架构设计

### 7.1 总体架构
建议采用分层架构：

1. **接入层**
   - 微信服务号/公众号/小程序
   - 医护工作台 Web
   - 管理后台 Web
   - 设备接入 API

2. **业务应用层**
   - 活动管理服务
   - 档案管理服务
   - 风险分层服务
   - 随访管理服务
   - 预警工单服务
   - 内容与群运营服务
   - 服务包与订单服务
   - 报表分析服务

3. **AI 中台层**
   - 知识库检索
   - AI 问答与随访编排
   - 内容生成
   - 随访摘要生成
   - 风险提示生成

4. **数据层**
   - 业务数据库
   - 日志数据库
   - 对象存储
   - 缓存
   - 分析型数据库

5. **集成层**
   - 设备接口
   - 消息接口
   - 支付接口
   - HIS/公卫系统接口
   - 短信/企业微信接口

以下为建议选型，可根据团队现状调整：

#### 前端
- 管理后台：Vue 3 + TypeScript + Element Plus
- 医护工作台：Vue 3 / React
- 小程序：原生小程序或 Taro/UniApp

#### 后端
- Java Spring Boot / Kotlin Spring Boot，或 Node.js NestJS
- RESTful API + Webhook
- 定时任务与工作流引擎

#### 数据层
- MySQL / PostgreSQL
- Redis
- Elasticsearch（可选，用于搜索与日志）

#### AI 层
- 大模型调用网关
- RAG 知识库
- 提示词模板中心
- 会话审计与安全过滤器

### 7.3 多租户设计
- 租户级数据隔离。
- 租户级功能开关与套餐配置。
- 租户级活动模板、标签、规则、内容库隔离。
- 平台级运营模板可复制到租户侧。

## 8. 数据模型设计

### 8.1 核心实体
建议首期至少包含以下核心实体：

- tenant：租户
- organization：机构/站点
- user：平台用户
- resident：居民档案
- family：家庭档案
- family_member_relation：家庭成员关系
- health_record：健康记录
- metric_record：指标记录
- tcm_assessment：中医评估记录
- risk_level_record：风险分层记录
- service_package：服务包定义
- service_order：服务订单
- service_fulfillment：服务履约记录
- campaign：活动
- campaign_registration：活动报名
- lead：线索
- followup_plan：随访计划
- followup_task：随访任务
- alert_event：预警事件
- referral_record：复诊/转诊记录
- content_asset：内容资产
- group_operation：群运营记录
- ai_session：AI 会话记录
- audit_log：审计日志

### 8.2 核心关系说明
- 一个居民可属于一个或多个家庭场景，但主家庭归属唯一。
- 一个居民可参与多个活动。
- 一个居民可拥有多个服务订单。
- 一个居民可有多条风险分层历史。
- 一条预警对应一个居民、一类指标、一组处置记录。

### 8.3 指标记录表示例
建议 `metric_record` 包含以下字段：
- id
- tenant_id
- resident_id
- metric_type
- metric_value
- metric_unit
- source_type（设备/人工/接口）
- source_device_id
- measured_at
- status_flag
- created_by
- created_at

## 10. AI 能力设计

### 10.1 AI 能力边界
AI 主要承担以下职责：
- 标准化问答
- 健康宣教
- 随访触达与信息收集
- 风险提示与任务编排
- 内容脚本生成
- 随访摘要与工作建议生成

AI 不直接承担以下职责：
- 最终诊断
- 高风险医疗处置决定
- 开方与处方替代
- 未经人工确认的转诊决定

### 10.2 AI 知识库建设
知识库建议分层：
- 基础医学与中医科普知识
- 院方专家审定知识
- 服务包规则与话术库
- 随访 SOP 与预警规则
- 活动与宣教内容模板

### 10.3 AI 安全机制
- 敏感问答分类。
- 高风险问题强制转人工。
- 输出内容审计与抽检。
- 提示词模板版本管理。
- 用户隐私脱敏与最小化使用。

- 服务包可配置。

## 12. 合规与审计要求

### 12.1 医疗合规
- AI 仅辅助，不替代医生医疗决策。
- 健康建议与医疗建议分层标识。
- 关键医疗相关内容需医生审核。

### 12.2 数据合规
- 居民授权采集与使用范围明确。
- 采集、存储、使用、导出有记录。
- 隐私政策、用户协议、授权书在线留档。

### 12.3 审计要求
- 审计 AI 输出。
- 审计档案修改。
- 审计预警处置。
- 审计服务履约。
- 审计内容发布与审校。

## 16. 风险与应对建议

### 16.1 业务风险
- 院内多部门协作不顺。
- 医护对新流程执行不一致。
- 活动热闹但后续激活不足。

应对：
- 建立项目领导小组。
- 固化 SOP 与责任分工。
- 用看板与台账做日周月复盘。

### 16.2 技术风险
- 设备接口标准不统一。
- AI 输出不稳定或口径漂移。
- 微信生态消息触达限制。

应对：
- 建立统一接入层。
- 建立知识库与审校机制。
- 设计多渠道触达与失败补偿。

### 16.3 合规风险
- 医疗建议边界不清。
- 居民隐私授权不完整。
- 内容宣传不合规。

应对：
- 对 AI 设置边界与转人工规则。
- 上线电子授权与留痕机制。
- 建立发布前审核流程。

## 18. 结语
本开发文档的核心不是单纯建设一个工具型系统，而是建设一套围绕社区卫生服务中心的“数字化健康经营基础设施”。该 SaaS 平台应同时具备业务承接能力、医疗协同能力、AI 辅助能力、私域运营能力与经营分析能力，最终形成可持续的居民健康管理闭环与可复制的样板点模式。
